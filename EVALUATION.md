# Evaluating `Nagafi/moondream2-q4-onnx` for Stage 2

**Verdict: do not deploy.** On Eye-Q's own workload the quantized ONNX export
is **2.7× slower** and burns **6× more CPU** per query than the fp32 PyTorch
baseline it would replace. It does use **2.5× less memory**, which is the one
thing it is genuinely good at — but Stage 2 is not memory-bound on any target
board, and the trade goes the wrong way.

The interesting part is *why*, because the reason generalizes to any quantized
Moondream export and is worth knowing before the next one is tried.

---

## 1. What this model actually is

The repo is not what the name suggests. Three things to know before reading any
benchmark:

| | |
|---|---|
| `model_type` | `moondream1`, traced at `transformers` 4.38.2 |
| `library_name` | `transformers.js` — targeted at browser WebGPU |
| Lineage | re-publish of Xenova's ONNX conversion of an early Moondream2 |

Eye-Q pins revision `2024-08-26`. This export predates it, so **any comparison
here is cross-revision, not just cross-quantization.** A verdict difference
between the two is not necessarily a quantization artifact.

It is also packaged for a runtime that is not Python. `optimum` has no
`moondream1` architecture, so nothing off the shelf drives it — the three
graphs have to be wired together by hand
([onnx_moondream.py](app/pipelines/onnx_moondream.py)).

### Packaging defects found

Three, all of which had to be worked around before a single inference ran.
None are reachable from JavaScript, which is presumably why they shipped.

**1. `embed_tokens_q4.onnx` is not quantized.** Despite the `_q4` suffix it is
100% FP32 — one 51200×2048 table, 419.4 MB, zero quantization ops:

```
=== embed_tokens_q4.onnx ===
  initializer payload: 419.4 MB
    FLOAT           1 tensors      419.4 MB  (100.0%)
  quant-related ops: NONE
```

That is **28% of the advertised "1.5 GB" sitting at full precision.** It is a
pure `Gather` lookup, so fp16 would halve it with no measurable accuracy cost
and int8 would quarter it. The other two graphs *are* genuinely 4-bit
(`MatMulNBits` over UINT8-packed weights), so this looks like an oversight in
the conversion, not a deliberate choice.

**2. The tokenizer will not load in Python at all.** `<image>` is an added
token with id `-200`. The Rust `tokenizers` library types ids as `u32` and
rejects the file outright:

```
Exception: invalid value: integer `-200`, expected u32 at line 7 column 16
```

**3. The tokenizer's post-processor panics even after that is fixed.** The
`TemplateProcessing` block references special token `<|endoftext|>`, but its
`special_tokens` map is keyed `<s>`. The lookup misses and the library panics
with `no entry found for key`.

Both tokenizer defects are repaired at load time in `load_tokenizer()`. A test
pins the premise, so if upstream ever re-uploads a clean file the workaround
fails loudly and can be deleted rather than carried forever.

## 2. Method

Benchmarking a VLM on stock photos measures the wrong thing. Stage 2 never sees
a full frame — it sees a padded, context-dimmed crop of one person produced by
`crop_detection_focused()` after YOLO fires, and latency depends on the aspect
ratio and detail of exactly those crops.

So the fixtures are generated by running **the real Stage 1 over the real
clip** (`cctv_demo.mp4`), and the prompts are **the demo's own three rules
verbatim**, including the ` Answer with only Yes or No.` suffix the worker
appends. Crops are ~107×323 — tall and narrow, as a standing person is.

- 3 crops × 3 prompts = 9 measured queries per backend
- One warmup query first, excluded — the first inference pays for ORT arena
  allocation and lazy kernel selection, and folding that one-off into the
  median would overstate steady-state latency
- Peak RSS sampled on a background thread at 20 ms, because allocation peaks
  during load and the allocator hands pages back before it can be read after
  the fact
- Both backends capped at 16 new tokens and run greedy

Machine: Apple M2, 8 cores, 17.2 GB, macOS 26.5.1, Python 3.13.11,
onnxruntime 1.29.0, CPUExecutionProvider.

## 3. Results

| | ONNX q4 (ORT CPU) | PyTorch fp32 (baseline) | |
|---|---:|---:|---|
| **Median latency** | **10,363 ms** | **3,900 ms** | 2.7× slower |
| Mean / p90 | 10,351 / 10,768 ms | 4,166 / 4,714 ms | |
| Min / max | 9,686 / 10,848 ms | 3,781 / 5,248 ms | |
| **CPU per query** | **41.4 CPU-s** | **6.9 CPU-s** | 6.0× more |
| CPU utilization | 4.0× | 1.65× | |
| **Steady peak RSS** | **3,369 MB** | **8,588 MB** | 2.5× less |
| Peak RSS during load | 2,999 MB | 5,287 MB | |
| On-disk weights | 1,523 MB | 3,736 MB | 2.5× smaller |
| Load time | 1.9 s | 17.1 s | 9× faster |

Setting `intra_op_num_threads=4` to match the P-core count made it *slightly
worse* (10,893 ms median) and left utilization unchanged at 4.0× — ORT was
already scheduling about four cores. **Thread tuning is not the problem.**

### Where the time goes

This is the whole story:

| Stage | Median | Share |
|---|---:|---:|
| Vision encoder | 2,585 ms | 24.9% |
| **Decoder prefill** | **7,669 ms** | **74.0%** |
| Decode | 103 ms | 1.0% |

The prompt is **~751–765 tokens** (729 image tokens + BOS + ~22 text tokens).
The answer is **1 token** — "Yes" or "No", exactly as the rules ask.

So the workload is **99% prefill, 1% decode**, and that is the wrong shape for
weight quantization:

- **Decode is memory-bandwidth-bound.** Quantization is a large win there —
  and indeed decode measures 9.7 tok/s, perfectly respectable.
- **Prefill is compute-bound.** 4-bit weights must be dequantized before they
  can be multiplied, so `MatMulNBits` pays an unpacking cost on every GEMM.
  Meanwhile the fp32 baseline hands its GEMMs straight to Apple's Accelerate
  BLAS and its AMX units.

Quantization optimizes the 1% and taxes the 99%. A binary-verdict appliance
that generates a single token is close to the worst possible case for this
optimization — the exact opposite of a chatbot, where long generations make
quantization pay.

### Answers agree 6 times out of 9

| Crop | Rule | ONNX q4 | PyTorch |
|---|---|---|---|
| crop_00 | bending | Yes | Yes |
| crop_00 | ppe | No | No |
| crop_00 | carrying | **No** | **Yes** |
| crop_01 | bending | No | No |
| crop_01 | ppe | No | No |
| crop_01 | carrying | No | No |
| crop_02 | bending | **Yes** | **No** |
| crop_02 | ppe | No | No |
| crop_02 | carrying | **No** | **Yes** |

Both models produce clean, parseable Yes/No that `BinaryVerdictParser` handles
without ambiguity — the integration is sound. But they disagree on a third of
queries, and **nine queries cannot tell you which one is right.** The
disagreement is confounded between quantization loss and the revision gap from
§1; separating them would need a labelled set, which this evaluation does not
have. Treat 6/9 as a flag for further work, not as an accuracy measurement.

## 4. Edge suitability

The `.env.pi5` profile already budgets ~3 GB of an 8 GB board and routes Stage
2 to a quantized model behind llama.cpp. Against that target:

**Memory fits comfortably.** 3.37 GB steady peak, against 8.59 GB for the
baseline. This is the export's real strength, and it is the reason the fp32
in-process path is not viable on an 8 GB board at all. Note that RSS here
includes mmap'd weight pages and so varies with page-cache warmth — the two
load-phase figures in §3 differed by 1.4 GB between a cold and warm run for
this reason. Steady-state peak during inference is the number to trust.

**Latency does not fit.** 10.4 s on an M2, and `.env.pi5` already observes that
a Cortex-A76 is "several times slower" than an M-series core. That puts a
single verdict somewhere in the **30–60 s** range on a Pi 5 — which is why that
profile already raises `EYEQ_VLM_TIMEOUT_S` to 180. At 41 CPU-seconds per query
on a fanless SBC, sustained load would also thermally throttle the board, and
Stage 1 has to keep running on those same cores.

The cascade's whole premise is that Stage 2 wakes on an event and answers
before the scene changes. A 30–60 s verdict describes a frame that is long
gone.

**The comparison that actually decides deployment was not run.** `.env.pi5`
already chose llama.cpp/Ollama with a q4 GGUF, so the live question is ONNX
vs. llama.cpp, not ONNX vs. fp32 torch. Nothing here displaces that choice —
llama.cpp's ARM GEMM kernels are hand-tuned in a way ORT's `MatMulNBits` path
is not, and this result gives no reason to expect ORT to win. Benchmarking the
`openai_compat` backend against a llama.cpp server on the same crops is the
obvious next step, and it needs real Pi 5 hardware to mean anything.

---

## 5. Recommendation

**Do not adopt this export.** It loses on the axis that matters (latency), wins
on the axis that does not (memory), and carries a stale model revision plus
three packaging defects.

Keep the `openai_compat` + llama.cpp path that `.env.pi5` already specifies.

If ONNX is worth revisiting, the order of attack follows from §3:

1. **Attack prefill, not decode.** 74% of latency is one GEMM-heavy pass over
   729 image tokens. Reducing image tokens does more than any quantization.
2. **Fix `embed_tokens`.** 419 MB of FP32 lookup table is free to reclaim.
3. **Try a q8 export.** 8-bit dequant is cheaper per GEMM than 4-bit and may
   land closer to the fp32 GEMM path while keeping most of the memory win.
4. **Only then re-measure**, on the target board, against llama.cpp.

The code added here is not wasted either way: `OnnxMoondreamBackend` satisfies
the existing `VLMBackend` protocol, so any future ONNX export can be measured
by pointing `--model-dir` at it.

## 6. Reproducing

```bash
# Fixtures — real Stage 2 person crops from the demo clip
uv run python bench/make_fixtures.py --count 8

# The two backends compared above
uv run python bench/benchmark_vlm.py --backend onnx-q4
uv run python bench/benchmark_vlm.py --backend torch

# Thread sensitivity
uv run python bench/benchmark_vlm.py --backend onnx-q4 --threads 4

# What is actually quantized, and the graph signatures
uv run python bench/audit_quant.py models/moondream2-q4-onnx/onnx/*.onnx
uv run python bench/inspect_onnx.py models/moondream2-q4-onnx/onnx/decoder_model_merged_q4.onnx

# Driver tests (no weights needed)
uv run python -m pytest tests/test_onnx_moondream.py -q
```

Weights are not committed (`/models/` is gitignored). Fetch with:

```bash
huggingface-cli download Nagafi/moondream2-q4-onnx --local-dir models/moondream2-q4-onnx
```

Each run writes JSON to `bench/results/<backend>-<arch>.json`.

## 7. Limitations

- **n=9 per backend on one clip.** Enough to settle a 2.7× latency gap; not
  enough to say anything about accuracy.
- **Verdict disagreement is confounded** between quantization and the revision
  gap. Untangling it needs labelled ground truth.
- **Measured on an M2, not on target hardware.** The Pi 5 figures in §4 are
  extrapolations, explicitly flagged as such.
- **q4f16 decoder variant not measured.** It shares the same `MatMulNBits`
  prefill path, so it is unlikely to change the verdict — but that is an
  expectation, not a measurement.
- **llama.cpp not measured**, which as §4 notes is the comparison that would
  actually decide deployment.
